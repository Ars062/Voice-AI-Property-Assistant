# Voice AI Property Assistant — Plan and Implementation Write-up

Repository: <https://github.com/Ars062/Voice-AI-Property-Assistant>
Date: 2026-10-22
Runtime target: Windows 11, CPU only, Groq for LLM, PostgreSQL 16 in Docker

---

## 1. Objective

Turn a legacy "hotel voice agent" demo (FastAPI + LangGraph + SQLite + LiveKit)
into a working, grounded, CPU-only **property assistant** that can:

1. understand a spoken or typed housing request,
2. search a real PostgreSQL inventory safely,
3. answer follow-up questions from the same result set,
4. walk the user through a confirmed booking,
5. speak the answer and optionally animate an avatar.

Constraints set for the project:

- **No OpenAI API.** Groq is the only LLM provider.
- **No GPU.** Everything must run on a normal Windows laptop.
- **No text-to-SQL.** The model must not be the security boundary.
- **PostgreSQL is the source of truth**, with a read-only role for search.
- The result must be cloneable, runnable, and testable on another machine.

## 3. Plan

### 3.1 Architecture decisions

**Plan-to-SQL instead of text-to-SQL.** The LLM emits a JSON object that is
validated by Pydantic into `PropertyQueryPlan`; a builder compiles that plan
into parameterised SQL. This keeps the model away from table names, joins and
literals while still allowing natural language.

**PostgreSQL with two roles.** `postgres` owns the schema; `voice_readonly`
executes every search with `default_transaction_read_only=on`, an 8 s statement
timeout, and no access to `bookings`.

**Database-enforced booking safety.** A GiST exclusion constraint prevents
overlapping confirmed bookings under concurrency, and a unique
`idempotency_key` makes retries safe. Python is not trusted for either.

**Two-phase booking.** The assistant collects details and asks for explicit
confirmation before writing. Nothing is written on "book it" alone.

**Deterministic where correctness matters.** Result counts and summaries are
computed from SQL rows, not generated by the model. LLM prose is only used for
specific questions, and is discarded if it mentions data that is not in the
records.

**Optional, swappable voice layers.** STT, TTS and avatar are independent
interfaces. Missing models degrade gracefully (Piper → SAPI, MuseTalk →
puppet) and never block the text answer.

### 3.2 Target layout

```
app.py                 FastAPI + --check CLI
config.py              env-backed settings
llm.py                 Groq client, retries, JSON mode
database/              engines, ORM models
property/              plan → SQL builder → repository (read-only)
agent/                 sessions, prompts, guardrails, orchestrator
voice/                 audio, stt, tts, pipeline
voice/avatar/          puppet + CPU MuseTalk port
frontend/              Streamlit UI
sql/                   schema, roles, seed
scripts/               init_db, wait_for_db, fetch_assets, run_windows
tests/                 pytest suite
docs/                  this write-up and supporting documents
```

### 3.3 Delivery phases

1. Replace SQLite with PostgreSQL; design schema, roles and seed.
2. Implement validated query planning and safe SQL generation.
3. Implement conversation state, follow-up merging, answering and booking.
4. Add STT/TTS/avatar with CPU-safe defaults.
5. Rebuild the API and Streamlit UI.
6. Write tests, run them, verify against real Groq and a real database.
7. Write documentation, commit and push.

## 4. Implementation

### 4.1 Database

`sql/001_schema.sql` defines:

- `properties(id, name, property_type, address, city, region, postal_code, description)`
- `rooms(id, property_id, unit, room_type, bedrooms, bathrooms, rent, deposit, size_sqm, max_occupants, available_from, description)`
- `amenities(id, name)` and `room_amenities(room_id, amenity_id)`
- `policies(id, property_id, category, title, body)`
- `bookings(id, room_id, guest_name, check_in, check_out, status, idempotency_key, created_at)`
- `room_blocks(id, room_id, start_date, end_date, reason)`
- view `room_blocked_ranges(room_id, start_date, end_date, source)` — date ranges
  only, no guest data.

Constraints and indexes:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings ADD CONSTRAINT bookings_no_overlap
  EXCLUDE USING gist (
    room_id WITH =,
    daterange(check_in, check_out, '[)') WITH &&
  ) WHERE (status = 'confirmed');

ALTER TABLE bookings ADD CONSTRAINT bookings_idempotency_key_key
  UNIQUE (idempotency_key);
```

`sql/002_roles.sql` creates `voice_readonly` with:
`default_transaction_read_only = on`, `statement_timeout = '8s'`,
`idle_in_transaction_session_timeout = '15s'`; grants `SELECT` on inventory and
the blocked-ranges view; grants nothing on `bookings`.

`sql/003_seed.sql` provides synthetic data: 3 properties, 12 rooms, 10
amenities, 56 room-amenity links, 9 policies, 3 confirmed bookings and 1
maintenance block spanning 4 date ranges.

`scripts/init_db.py` applies the files in order and supports `--reset`
(drop/recreate app objects) and `--check` (counts and connection identity).
Docker Compose mounts `sql/` as initdb scripts and exposes PostgreSQL on host
port **5433** to avoid clashing with a local 5432.

Measured state after setup:

```
properties 3 | rooms 12 | amenities 10 | room_amenities 56
policies 9   | bookings 3 | room_blocks 1
current_user = voice_readonly, transaction_read_only = on
SELECT on bookings -> denied
```

### 4.2 Configuration

`config.py` is a small dataclass populated from `.env` with absolute-path
helpers. Key settings:

- `GROQ_API_KEY`, `GROQ_MODEL` (default `qwen/qwen3.8-27b`)
- `DATABASE_URL`, `DATABASE_READONLY_URL`
- `WHISPER_MODEL`, `WHISPER_MODEL_DIR`, `STT_PROVIDER`
- `TTS_PROVIDER` (`auto|piper|sapi`), `PIPER_MODEL`, `TTS_SAPI_VOICE` / `TTS_SAPI_RATE`
- `AVATAR_ENGINE` (`auto|puppet|musetalk`), `AVATAR_MAX_SECONDS`, `AVATAR_FPS`,
  `AVATAR_CPU_RENDER_FPS`, `AVATAR_CPU_THREADS`, `AVATAR_MUSETALK_DIR`,
  `AVATAR_MUSETALK_BBOX`, `AVATAR_BATCH_SIZE`, `AVATAR_MAX_WIDTH`
- session TTL, query row cap, statement timeout.

No secrets are committed: `.env` is ignored and `.env.example` documents every
field with placeholders.

### 4.3 LLM layer (`llm.py`)

- Groq SDK only (`from groq import Groq`), no OpenAI package.
- Browser-like client defaults, request timeout, retry with backoff for
  transient errors, and clear `LLMError` messages.
- `complete_json()` uses `response_format={"type":"json_object"}` and validates
  the parsed JSON, with one repair attempt.
- `ping()` powers `python app.py --check`.

Model audit: the provided Groq key exposes 11 models; the hard-coded
`llama-3.3-70b-versatile` is retired on that account. `qwen/qwen3.8-27b` was
selected because it is chat-capable and returns clean JSON. A `403` seen during
testing was Cloudflare rejecting a bare `urllib` user agent, not authentication.

### 4.4 Query pipeline (`property/`)

1. **`query_plan.py`** — `PropertyQueryPlan` with typed fields:
   `city`, `property_name`, `property_type`, `room_type`, `min_rent`, `max_rent`,
   `min_size_sqm`, `min_occupants`, `amenities`, `available_from`,
   `available_to`, `sort_by`, `limit`. Validation rejects negative rent,
   inverted dates, invalid sort keys and `limit > QUERY_MAX_ROWS`.
2. **`sql_builder.py`** — one `SELECT` with joins to properties, amenities and
   the blocked-ranges view. Every value is a bind parameter. Only the `ORDER BY`
   and table/column names come from allow-listed constants.
3. **`repository.py`** — executes on `read_session()` (read-only role), groups
   amenities per room, returns `RoomRecord` objects, and exposes availability and
   booking helpers used by the agent.
4. **`validator.py`** — defense-in-depth for any future raw SQL: single
   `SELECT`/`WITH` only, no comments or `;`, blocked DDL/DML tokens and system
   schemas/functions, all table references checked against `ALLOWED_TABLES`
   (CTEs handled).
5. **`tools.py`** — thin façade used by the agent and tests.

Example verified query: "2 bedroom with parking in Austin under 1800" compiles
to parameters `city='Austin'`, `room_type='2 bedroom'`, `max_rent=1800`,
`amenities=['parking']`, and returns rooms 2, 3 and 9 (and 4/11 for the pet
variant).

### 4.5 Agent (`agent/`)

`context.py`

- `ConversationState` holds turns, the last merged plan, last results, selected
  room and a pending booking.
- `SessionStore` is thread-safe, TTL 7200 s, max 500 sessions, with reset.

`orchestrator.py`

- `Assistant.handle(text, session_id)`:
  - reset phrases ("start over", "new search") clear the plan and results;
  - booking intent routes to the booking branch;
  - otherwise extract a plan, merge it, query, answer, and optionally prepare a
    booking.
- `_merge_plan` keeps previous scalar filters unless the new turn explicitly
  changes them, unions amenities, and lets "cheapest/largest/newest" override
  sorting. This exists because the model tends to drop previously stated
  filters on follow-ups.
- Answering rules:
  - plain searches return a deterministic counted summary (`format_rooms`);
  - specific questions call the LLM with only the returned records;
  - `guardrails.grounding_issues()` rejects replies that mention unknown room
    ids or prices, falling back to the deterministic summary;
  - no-match turns use `NO_MATCH_REPLY` instead of inventing inventory.

`guardrails.py` also provides `is_affirmative`, `is_negative`,
`has_booking_intent`, `asks_about_policies`, `is_specific_question`,
`ordinal_index`, `pick_cheapest`, `pick_room`, `format_rooms` and
`format_details`.

`prompts.py` keeps the plan, answer and booking prompts versioned in code so
changes are reviewable.

### 4.6 Booking flow

```
"book the cheapest one for Jane Doe 2027-03-01 to 2027-09-01"
  -> LLM extracts room + guest + dates (validated)
  -> room must exist in the current result set
  -> availability check against confirmed bookings and blocks
  -> pending_booking token, no write
  -> "Please confirm: ... reply yes"

"yes"
  -> create_booking(idempotency_key = session:token)
  -> INSERT ... RETURNING
  -> exclusion constraint / unique key resolves races
  -> "Booked. Your booking id is N"

"no"
  -> pending cleared, nothing written
```

Ambiguous answers keep the pending booking and ask again. Two-phase
confirmation plus idempotency means a retried "yes" cannot create a duplicate.

### 4.7 API (`app.py`)

FastAPI endpoints:

- `GET /`, `GET /health`, `GET /meta`
- `POST /chat`, `POST /voice`, `POST /stt`, `POST /tts`
- `GET /rooms`, `GET /avatar/portrait`, `DELETE /sessions/{id}`

Notable behaviours:

- `/health` returns `503` when PostgreSQL is unreachable and reports LLM/TTS/
  avatar availability without leaking secrets.
- `/voice` accepts wav/webm/opus/mp3 up to 15 MB, transcribes, then runs the same
  pipeline as `/chat`.
- `/chat` and `/voice` return base64 WAV and GIF alongside JSON when requested;
  a speech or avatar failure never removes the text answer.
- database engines use a 5 s connect timeout so an offline Docker engine fails
  fast instead of hanging.
- `python app.py --check` prints key/model presence, database counts, TTS and
  avatar readiness, and a live Groq ping.

### 4.8 Voice

**Audio (`voice/audio.py`)** — decode, resample, normalise, WAV encode, RMS,
base64. Uses PyAV for browser formats.

**STT (`voice/stt.py`)** — faster-whisper `WhisperModel`, CPU, `int8`,
`vad_filter=True`, `beam_size=1`; lazy loading; model cached under
`WHISPER_MODEL_DIR`.

**TTS (`voice/tts.py`)** — `auto` prefers Piper if the package and `.onnx` file
exist, otherwise Windows SAPI through a PowerShell subprocess (avoids the
COM/thread problems of `pyttsx3` in a server). `describe()` drives `/health`.

**Avatar (`voice/avatar/`)**

- `base.py`: `AvatarClip`, `AvatarError`, GIF encoding.
- `puppet.py`: generates `assets/portrait.png` if absent, pre-renders 8 mouth
  shapes and selects one per frame from smoothed RMS. Fast; default.
- `musetalk_cpu.py`: CPU port of MuseTalk 1.5 (see §5).
- `engine.py`: `build_avatar()` chooses MuseTalk when ready, else puppet; never
  raises.

### 4.9 Frontend (`frontend/streamlit_app.py`)

Chat input, `st.audio_input` microphone capture, audio playback, avatar GIF,
per-room expanders with amenities, pending-booking display, health sidebar and
session reset. Calls the API at `API_URL` (default `http://127.0.0.1:8000`).

## 5. MuseTalk on CPU

### Plan

MuseTalk upstream assumes CUDA and pulls `triton`, mmpose, face-parsing and
librosa. The plan was to keep the model maths but remove GPU-only and
orchestration-heavy pieces so it can run on CPU, while accepting that it is
slower than real time and therefore optional.

### Implementation (`voice/avatar/musetalk_cpu.py`)

Pipeline per reply:

1. load portrait, detect/use configured face bounding box;
2. resample audio to 16 kHz and extract Whisper features;
3. split features into one prompt chunk per rendered frame;
4. run the MuseTalk UNet over cached portrait latents;
5. decode the lower-face crop with SD-VAE;
6. feather and paste the crop back onto the portrait;
7. repeat rendered frames to the output frame rate and encode a GIF.

CPU changes:

- device CPU, dtype `float32`;
- no `triton`/CUDA imports anywhere;
- `torch.inference_mode()`, no autograd;
- render at `AVATAR_CPU_RENDER_FPS` (default 6) and repeat to `AVATAR_FPS`
  (default 25) — the largest saving;
- optional int8 dynamic quantization of UNet `Linear` layers;
- optional `torch.set_num_threads(AVATAR_CPU_THREADS)`;
- `AVATAR_MAX_SECONDS` and `AVATAR_MAX_WIDTH` cap work;
- lazy imports so the core install never needs torch.

### Present status

- Code: implemented (`~15 KB`), covered indirectly by avatar tests only for the
  puppet engine.
- Runtime: **not installed** — `torch`/`diffusers`/`transformers` are absent and
  `models/musetalk` is empty. `/health` correctly reports
  `musetalk_ready: false`.
- Enable with:
  ```powershell
  pip install -r requirements-avatar.txt
  .\.venv\Scripts\python.exe scripts\fetch_assets.py --musetalk
  ```
  then place `assets/portrait.png` and set `AVATAR_ENGINE=musetalk`.

This is the one part of the stack that has not been executed end to end on this
machine.

## 8. Limitations and next steps

1. Sessions are in-memory; a restart loses context and scaling needs Redis.
2. No authentication; keep it bound to localhost or add auth/CORS restrictions.
3. Bookings are demo-grade: no identity, payment or contract verification.
4. STT is installed but not yet exercised end to end with a real microphone.
5. MuseTalk needs torch, weights and validation on this hardware; puppet remains
   the default.
6. SAPI is Windows-only; Piper is the cross-platform path.
7. In-memory transcripts live for the session TTL (2 h); audio itself is not
   persisted.
